# DevOps Pet Project: Автоматизация развертывания веб-приложения

## Что это за проект?

Это учебный проект, в котором я реализовал полный цикл разработки и доставки веб-приложения — от написания кода до автоматического деплоя. Проект демонстрирует базовые навыки DevOps-инженера: контейнеризацию, оркестрацию, CI/CD и работу с инфраструктурой как кодом.

---

## Как это работает? (Простыми словами)

Представь, что ты разработчик, который написал новое приложение. Раньше, чтобы его запустить на сервере, нужно было:
1. Зайти на сервер по SSH
2. Установить Python, зависимости, Nginx
3. Скопировать код
4. Запустить приложение
5. Если что-то сломалось — повторить всё заново

**Проблема:** Это долго, вручную, и на разных серверах может работать по-разному ("у меня на компьютере работало!").

**Решение:** Упаковать всё в **Docker-контейнер** (как в коробку, где есть всё необходимое) и настроить **автоматическую доставку** через CI/CD.

## Подробное описание каждого компонента

### 1. Приложение (app.py)

Простое веб-приложение на Python с использованием фреймворка Flask.

**Что делает:**
- Отвечает на запрос `GET /` текстом "Hello from my Docker container!"
- Отвечает на запрос `GET /health` текстом "OK" (для проверки, что приложение живо)

**Почему Flask?**
Flask — это минималистичный фреймворк, который позволяет за 5 строк кода создать веб-сервер. Идеально для учебных проектов.

**Важный момент:**
Приложение слушает `0.0.0.0:5000`, а не `127.0.0.1:5000`. Это критически важно для Docker, потому что контейнер — это изолированная среда, и `127.0.0.1` внутри контейнера означает "только сам контейнер", а не хост-машина.

### 2. Dockerfile

Файл, который говорит Docker, как собрать образ нашего приложения.

**Пошаговое объяснение:**

```dockerfile
FROM python:3.11-slim

Берем готовый базовый образ с Python 3.11. Флаг slim означает обрезанную версию — меньше размер, меньше потенциальных уязвимостей.
    WORKDIR /app
Создаем рабочую директорию внутри контейнера и переходим в нее.
    COPY requirements.txt .
Копируем файл зависимостей из нашего компьютера в контейнер.
    RUN pip install --no-cache-dir -r requirements.txt
Устанавливаем Python-библиотеки внутри контейнера. Флаг --no-cache-dir экономит место.
    COPY app.py .
Копируем код приложения в контейнер.
    EXPOSE 5000
Документируем, что приложение будет использовать порт 5000
    CMD ["python", "app.py"]
Команда, которая запустится при старте контейнера.
3. Nginx (nginx.conf)
    Nginx — это веб-сервер, который работает как Reverse Proxy (обратный прокси).
    Зачем он нужен?
        Принимает запросы от пользователей на стандартном порту 80
        Перенаправляет их на наше Flask-приложение (порт 5000)
        Скрывает реальную структуру приложения от внешнего мира
        Может добавлять SSL, кэширование, балансировку нагрузки
Конфигурация:
    server {
    listen 80;  # Слушаем порт 80 (стандартный HTTP)

    location / {
        proxy_pass http://app:5000;  # Перенаправляем на Flask
        # Передаем информацию о реальном клиенте
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        }
    }
4. Docker Compose (docker-compose.yml)
Файл, который описывает всю инфраструктуру проекта и позволяет запускать её одной командой.
Объяснение:
services:
  app:
    image: mylesgwy/portfolio-app:latest  # Образ из Docker Hub
    build: .                              # Или собрать локально
    expose:
      - "5000"                            # Порт доступен только внутри сети Docker
Почему expose, а не ports?
ports — пробрасывает порт на хост-машину (доступно извне)
expose — открывает порт только для других контейнеров внутри Docker-сети
Это принцип безопасности: Flask не должен быть доступен напрямую из интернета, весь трафик должен идти через Nginx.
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"                           # Пробрасываем порт 80 на хост
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - app                               # Ждем запуска app перед стартом nginx
5. GitHub Actions (ci.yml)
Автоматизированный пайплайн, который запускается при каждом git push.
Как работает:
on:
  push:
    branches:
      - main
Триггер: запускать при пуше в ветку main.
jobs:
  build-and-push:
    runs-on: ubuntu-latest
Создаем job, которая будет выполняться на сервере Ubuntu от GitHub.
    steps:
      - name: Checkout code
        uses: actions/checkout@v4
Шаг 1: Скачиваем код из репозитория на сервер.
      - name: Log in to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_PASSWORD }}
Шаг 2: Логинимся в Docker Hub. Пароли берутся из GitHub Secrets — безопасного хранилища, где они не видны в коде.
      - name: Build and push Docker image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ secrets.DOCKER_USERNAME }}/portfolio-app:latest
      - name: Build and push Docker image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ secrets.DOCKER_USERNAME }}/portfolio-app:latest
Шаг 3: Собираем образ и отправляем его в Docker Hub.
6. Скрипт деплоя (deploy.sh)
Bash-скрипт, который обновляет приложение на сервере.
Что делает:
docker compose pull
    Скачивает последние версии образов из Docker Hub.
docker compose up -d --force-recreate
    Пересоздает контейнеры с новыми образами. Флаг --force-recreate гарантирует, что контейнеры будут пересозданы даже если Docker считает их актуальными.
docker image prune -f
    Очищает старые, неиспользуемые образы, чтобы не забивать диск.
CI/CD Pipeline: Пошаговый процесс
Шаг 1: Разработка
Разработчик вносит изменения в код (например, меняет текст приветствия).
Шаг 2: Коммит и пуш
git add app.py
git commit -m "Update welcome message"
git push
Шаг 3: Автоматическая сборка (CI)
GitHub Actions автоматически:
Скачивает код из репозитория
Логинится в Docker Hub (используя секреты)
Собирает новый Docker-образ
Отправляет образ в Docker Hub с тегом latest
Шаг 4: Деплой (CD)
На сервере выполняется скрипт:
./deploy.sh
Который:
Скачивает новый образ из Docker Hub
Пересоздает контейнеры
Очищает старые образы
Шаг 5: Проверка
Открываем браузер и видим обновленное приложение!
